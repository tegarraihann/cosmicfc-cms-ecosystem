01 · Tujuan & Scope

Satu Aset, Banyak Konten.

Media Library menggantikan mekanisme pemindaian folder storage menjadi katalog aset berbasis database. Admin dapat mengunggah, mencari, memilih, memperbarui metadata, mengetahui lokasi pemakaian, dan menghapus media secara terkendali.

Keputusan utama: file fisik disimpan pada disk, sedangkan identitas, metadata, status, pemilik, dan pemakaiannya dicatat di database. Konten menyimpan referensi media, bukan menduplikasi file.

Discoverable

Pencarian nama, alt text, kategori, tag, tipe, dan tanggal.

Reusable

Satu foto dapat dipakai oleh beberapa section tanpa upload ulang.

Safe Delete

Media yang sedang dipakai tidak dapat dihapus tanpa penggantian.

Traceable

Uploader, waktu, perubahan metadata, dan penghapusan tercatat.

03 · Upload & Processing

Alur Upload.

Pilih / Drop File→Validasi→Simpan File→Baca Metadata→Buat Record
TahapPerilaku
Client validationFormat, jumlah, dan ukuran diperiksa sebelum request; preview lokal dan progress per file.
Server validationMIME aktual, extension whitelist, maksimum 5 MB, nama folder whitelist, dan permission upload.
FilenameNama fisik menggunakan UUID; nama asli hanya menjadi metadata untuk mencegah collision.
MetadataLebar, tinggi, MIME, bytes, checksum, uploader, disk, path, dan waktu upload.
OptimizationOrientasi dinormalisasi; versi awal mempertahankan original. Thumbnail/optimasi dapat ditambah terpisah.
DuplicateChecksum mendeteksi file identik dan menawarkan memakai aset lama.

04 · Model Data

Struktur Penyimpanan.

media ├── id, uuid ├── disk, directory, filename ├── original_name, extension, mime_type ├── size_bytes, width, height, checksum ├── title, alt_text, caption ├── folder // general | players | matches | sponsors ├── status // active | archived ├── uploaded_by, deleted_by ├── deleted_at // soft delete └── timestamps media_tags ├── id, name, slug └── timestamps media_tag ├── media_id └── media_tag_id media_usages ├── media_id ├── usable_type, usable_id // polymorphic consumer ├── field_key // heroImage, photo, logo_url... └── timestamps media_audits ├── media_id, user_id, action ├── before_payload, after_payload └── timestamps

Referensi Konten

Target akhir adalah menyimpan media_id. Selama migrasi dari field URL, sistem dapat mendukung keduanya: ID menjadi prioritas, URL lama menjadi fallback. Resolver media mengembalikan URL publik dan metadata alt.

Database record dan file harus diperlakukan sebagai satu transaksi logis. Jika penyimpanan database gagal, file yang baru dibuat harus dibersihkan.

06 · Delete, Usage & Security

Proteksi Aset.

AksiAturan
Hapus media tidak dipakaiSoft delete record; file dapat masuk trash retention.
Hapus media sedang dipakaiDitolak dan tampilkan daftar konsumen serta tautan edit.
Force deleteDi luar v1; hanya superadmin setelah retention dan audit.
RestoreMengaktifkan kembali record selama file masih tersedia.
Ganti mediaReplace reference per konsumen; tidak menimpa binary aset lama.

Permission

PermissionKemampuanDefault
media.viewMelihat library, detail, dan usage.Admin
media.uploadUpload dan mengisi metadata awal.Admin
media.updateUbah title, alt, caption, folder, dan tag.Admin
media.deleteSoft delete media yang tidak digunakan.Admin terbatas
media.restoreMemulihkan media terhapus.Superadmin
  • Gunakan MIME sniffing server-side; jangan percaya extension browser.
  • SVG tidak diterima pada v1 untuk menghindari payload aktif.
  • Nama path tidak berasal dari input bebas dan tidak boleh mengandung traversal.
  • Endpoint upload diberi throttle serta batas jumlah file.
  • Alt text diwajibkan saat media dipilih untuk konten publik, kecuali gambar dekoratif.

07 · API & Migration

Endpoint dan Transisi.

MethodEndpointTujuan
GET/admin/mediaHalaman library.
GET/admin/media/itemsQuery paginated untuk library/picker.
POST/admin/mediaUpload satu atau banyak file.
PUT/admin/media/{media}Perbarui metadata.
DELETE/admin/media/{media}Soft delete dengan usage guard.
POST/admin/media/{media}/restorePulihkan media.
GET/admin/media/{media}/usagesDaftar lokasi pemakaian.

Strategi Migrasi

Scan uploads→Hash & Metadata→Buat Record→Cocokkan URL→Isi Usage
  1. Import file lama secara idempotent berdasarkan path/checksum.
  2. Jangan memindahkan file fisik pada migrasi pertama agar URL lama tetap hidup.
  3. Petakan field URL existing ke media ID jika ditemukan.
  4. Tandai file orphan untuk review, bukan langsung menghapus.
  5. Setelah konsumen memakai picker, hentikan pemindaian folder langsung.

08 · Acceptance & Risks

Kriteria Penerimaan.

  • Admin dengan permission dapat membuka Media Library dari sidebar.
  • Upload JPG/PNG/WebP maksimal 5 MB menghasilkan record dan preview.
  • File tidak valid ditolak tanpa menyisakan file orphan.
  • Library dapat dicari dan difilter dengan pagination server-side.
  • Metadata gambar dan uploader tampil pada drawer detail.
  • Perubahan title/alt/folder/tag tercatat pada audit.
  • Picker yang sama bekerja pada Profil Klub dan Section Editor.
  • Media yang sedang digunakan tidak dapat dihapus.
  • Media tidak terpakai dapat di-soft-delete dan dipulihkan sesuai permission.
  • Tampilan desktop dan smartphone tetap usable.
  • Import file lama dapat dijalankan ulang tanpa duplikasi.
  • Feature test mencakup permission, upload, filter, update, usage guard, delete, dan restore.

Risiko & Mitigasi

RisikoMitigasi
File dan database tidak sinkron.Cleanup saat gagal, audit command, dan health check.
Menghapus gambar yang tampil.Usage registry, delete guard, soft delete.
Library lambat.Index database, thumbnail, pagination, lazy loading.
Duplikasi aset.Checksum dan dialog reuse existing.
Upload berbahaya.MIME sniffing, whitelist, UUID filename, SVG ditolak.
